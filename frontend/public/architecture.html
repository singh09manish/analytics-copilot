Analytics Copilot

A plain-English question, an auditable answer.

Analytics Copilot is a chat interface where a business user asks a question in plain English and gets the answer back from a governed Snowflake warehouse. Every answer that ran a query carries the SQL that produced it, so any number on the screen can be traced back to the query behind it.

This page is the architecture behind the demo: how a question travels, what the agent actually does, and where the boundaries are. It is written to be checked — everything below is drawn from the code, and the honest limits are set out at the end.

React 19 + Vite CloudFront + S3 FastAPI on ECS Fargate LangGraph MCP tool server Snowflake sqlglot guard Claude via the Anthropic API
01

How a question travels

One hostname, two origins. Static files come from S3; anything under /api/* goes to the load balancer in front of a single ECS Fargate task that runs both the API and the agent. The role split on the right is the point of the whole system, so it is drawn rather than described.

02

The agent graph

Every node and every edge of the LangGraph StateGraph, transcribed from backend/src/copilot/agent/graph.py. Four nodes call the model; five are deterministic. Every path converges on remember, so a turn is recorded whether it succeeded or failed.

03

How governance is enforced

Three layers, each with a different failure mode, so that no single one has to be right. What each layer does not do matters as much as what it does.

Layer 1 — in the app

sqlglot guard

Parses the model's SQL and admits exactly one statement: a SELECT (or a set operation over SELECTs), every table qualified to MEDTECH_ANALYTICS.GOLD, no DML or DDL, no LATERAL, no table functions, no GET_DDL or SYSTEM$…, and a LIMIT rewritten to at most 1000.

Does notCheck that the query is right. It reasons about the shape of SQL, not about entitlement — a query can clear the guard and still answer the wrong question.

Layer 2 — at the tool boundary

MCP tool server

Re-runs that identical validation — literally the same validate() from the same module — on whatever SQL it is handed, and refuses any Snowflake role outside COPILOT_APP_RO and COPILOT_ADMIN. It is a stdio server any client can drive, so it does not trust its caller.

Does notAuthenticate anybody. It never sees the JWT and has no idea who the user is; it only refuses to widen what it was asked to do.

Layer 3 — in the warehouse

Snowflake role grants

COPILOT_APP_RO holds SELECT on GOLD and on exactly two tables in the COPILOT schema — the schema cards and the glossary. Everything else there, REQUEST_LOG included, was explicitly revoked.

Does notFilter rows or judge intent. This is the layer that holds when the other two are wrong: the role cannot reach what it was never granted, whatever the SQL says.

Masking GOLD.DIM_TREATMENT_CENTER is a Snowflake secure view, and contact_email is a CASE on CURRENT_ROLE(): ***MASKED*** for COPILOT_APP_RO, the real value for COPILOT_ADMIN. The unmasked source rows live in SILVER, which the read-only role has no grant on at all — so the mask is not something a cleverer query can route around. It is a view, not the native masking policy, for the reason set out below.

04

What this is, and what it is not

This is a demo built to show a data path end to end, not a system carrying production load. The limits below are deliberate choices with reasons, not gaps waiting to be found.

The data
Synthetic. 60 treatment centres, their radiotherapy machines, two years of daily utilization, and service tickets — generated deterministically by a seed script. No patient data of any kind and no real customer data; contact_email is the stand-in for PII.
Deployment
One region (us-east-1), one ECS Fargate task, desired count of 1. No autoscaling and no multi-AZ redundancy in the application tier. Enough to demonstrate the path; not sized for anyone's traffic.
Conversation memory
Held in the process — a bounded LangGraph checkpointer with an LRU over conversation threads, not Redis. A task restart drops history, and a second task would not share it. The bound is there partly for governance: it puts a ceiling on how long an admin's unmasked rows survive the request that produced them.
Column masking
Implemented as a secure view rather than a native MASKING POLICY, because the trial account is Snowflake Standard edition and masking policies require Enterprise. The observable behaviour across these two roles is the same; the mechanism is not. The Enterprise DDL is written out, commented, in the governance script.
Authentication
Two fixed demo accounts with bcrypt-hashed passwords and HS256 JWTs on an 8-hour TTL. No identity provider, no SSO, no user directory — the JWT exists to carry a role claim into a Snowflake role, which is the part worth demonstrating.
The model
Claude, called through the Anthropic API for four things only: classifying intent, drafting SQL, defining a glossary term, and writing the prose summary over rows that Snowflake returned. The model never sees the warehouse directly and never chooses which role executes a query.

The app is live at d9hwkll0kck56.cloudfront.net. The credentials for the two accounts were sent in the email — this page is public and unauthenticated, so it carries none.

The quickest way to see the point of it: sign in as the analyst and ask for the treatment centres with their contact emails, then sign in as the admin and ask exactly the same question. The generated SQL underneath both answers is identical. Only the column changes.
